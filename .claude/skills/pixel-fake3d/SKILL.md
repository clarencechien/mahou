# mahou pixel art 假 3D 風格聖經

所有遊戲畫面共用同一套視覺語言。這份文件的每個數字都經過本 repo 實測（容器軟體渲染 ＋ Chromebook 實機），不是美學偏好。

## 0. 不可違反的三條

1. **內部低解析度 ＋ 整數倍放大**。畫面一律畫在小緩衝區（大螢幕 320×180、手機直式 160×284、mockup 256×144），用 `image-rendering: pixelated` 放大。禁止直接在全解析度 canvas 上畫「像素風」。
2. **每個場景一個受限調色盤，10–14 色**。顏色一多就變成「縮小的照片」。調色盤定義在場景頂部，全場景只從裡面取色（shade/mix 的結果除外）。
3. **構圖用形狀，質感用抖動**。用多邊形、帶子、橢圓把構圖畫出來；抖動只負責交界處的過渡。反過來（用雜訊堆構圖）一定失敗——星夜第一版就是這樣毀的。

## 1. 效能預算（實測值，超過再優化）

| 情境 | 實測 | 60fps 預算餘裕 |
|---|---|---|
| Chromebook WebGL 12 分割（1872×1053） | 1.0ms/幀 | 16× |
| Canvas2D 掃描線 8 分割 | 3.2ms/幀（實機） | 5× |
| 名畫級複雜場景重繪一次（320×180 像素緩衝） | ~11ms | 一次性，可接受 |
| 快取底圖後的每幀成本（blit＋精靈＋游標） | 0.3ms | 55× |

**結論先背起來：分割數不是成本（總像素固定），複雜靜態背景要畫一次快取起來，會動的東西才逐幀畫。**

## 2. 核心配方（複製即可用，出處 public/game6.html）

### 2.1 Bayer 4×4 有序抖動 ＋ smoothstep punch
```js
const BAYER = [[0,8,2,10],[12,4,14,6],[3,11,1,9],[15,7,13,5]];
const bayer = (x, y) => (BAYER[y & 3][x & 3] + 0.5) / 16;
const ss = (t) => { t = Math.max(0, Math.min(1, t)); return t * t * (3 - 2 * t); };
const punch = (v, k = 3) => ss((v - 0.5) * k + 0.5);   // k=2~5
// 用法：mix 值先 punch 再跟 bayer(x,y) 比大小決定取哪一色
```
**為什麼要 punch**：抖動直接吃連續的 mix 值會整片變雜訊。punch 把值推向 0/1，色塊變實心、抖動只留在交界，看起來才是「筆觸」。

### 2.2 色相偏移著色（取代加減亮度）
```js
const shade = (c, amt) => amt < 0
  ? [c[0]*(1+amt), c[1]*(1+amt*.88), c[2]*(1+amt*.62)]              // 暗部偏冷（藍紫）
  : [c[0]+(255-c[0])*amt, c[1]+(255-c[1])*amt*.92, c[2]+(255-c[2])*amt*.6]; // 亮部偏暖（黃）
```
單純調亮度會發灰發髒。任何陰影／高光都走這個函式。

### 2.3 Mode 7 地面（假 3D 的地板）
```
z = f / (y - horizon)          // f≈90，每條掃描線一個深度
一格在螢幕上的寬度 = cell * f / z
世界座標 wx = (x - W/2) * z / f + camX；捲動 = z + scroll
```
兩條實作路線都已驗證：Canvas2D 逐掃描線 `drawImage` 條帶縮放（SFC 原味，8 分割 3.2ms）；WebGL fragment shader 射線（12 分割 1.0ms，多人分割一律用這條＋`gl.viewport` 切格，單一 context 一次提交）。遠處 `cw < 2.2px` 直接填單色（far color），省掉子像素雜訊。

### 2.3.1 速度感三件套（三個都不用改玩法）

速度感來自**每秒有多少東西刷過畫面**，不是玩家自己跑多快。三個旋鈕，成本都接近零：

| 手法 | 做法 | 效果 |
|---|---|---|
| **廣角** | 速度越快 `f` 越小（mahou：`f = 94 - sp01*16`） | 兩側掃得更兇。太廣會像魚眼 |
| **地面花紋** | 只縮放紋理取樣座標（`tex`），不動幾何 | 難度完全不變的純視覺加速。太高會閃爍（取樣頻率超過像素格） |
| **固定間距的路邊物件** | 路標／標竿**不隨速度倍率放大間距** | 速度越快掠過越兇，順便標出賽道邊界。SFC 賽車的老招 |

**進入「超速狀態」時三個一起推**，不要只加一個紅框：mahou 的滑雪每升一檔超加速就
`f -= 5`、`tex *= 1.22`。玩家才看得出來是**換了一檔**，而不是分數變大而已。
只給紅框＋加速度的版本實測是「沒有真的超加速感」——狀態要能從畫面本身讀出來。

#### 多段超速：級距要放大，名字要不一樣

同一件事踩了第二次。mahou 的滑雪本來就有三級（3／6／9 連），但玩家的回報是
**「超加速只有一段」**——因為三級全都叫「超加速」、畫面長一樣、升級的推力也都是固定的 +6。
機制升了級，人讀不出來，等於只有一段。三條規則：

| | 錯的做法 | 對的做法 |
|---|---|---|
| **級距** | 每級固定 +6 | `+base × lv`（6／12／18）。第二段要比第一段更用力，不然只是第一段再久一點 |
| **名字** | 「超加速」「超加速 2」「超加速 3」 | 三個**不同的詞**，一眼分得出強弱（超加速 → 極速 → 神速） |
| **畫面** | 只換框線顏色 | 三個旋鈕的級距也要放大：`f` −5／−12／−20、`tex` ×1.22／×1.55／×1.95、框線 2／6／8px＋內框 |

**閃動要有底線。** 純脈動（`0.35 + 0.3·sin t`）會週期性掉到接近透明，在電視上讀起來是
閃爍不是狀態；更糟的是高檔位在低谷時會比低檔位還淡，換檔反而看起來像降檔。
底線要跟著檔位抬：`0.3 + lv×0.12 + 0.3·sin t`。

**「花紋太細會閃爍」要量，不要用猜的。** 把幾格**鎖成同一個速度**、只讓 `tex` 不同，
連拍 20＋幀比對相鄰兩幀的地面像素差：差值持平＝沒有多出來的取樣雜訊。
mahou 實測 ×1.0/1.22/1.55/1.95 四檔的平均差是 31.9 / 31.3 / 32.0 / 33.2——持平，
所以 ×1.95 是安全的。不控住速度就量不到這件事：跑比較快本來就會差比較多。

**手機端的檔位底色要驗對比。** 底色一路往「燒起來」的方向走（暗紅 → 橘 → 亮黃）時，
寫死的白字／灰字會在最亮那一檔失效：mahou 的副標在橘底上只有 3.7:1。
底色會換，字色就得跟著換（亮黃那檔連字色一起改成深紫），四檔全部量過再收工。

### 2.4 深度精靈（樹、旗、方塊、對手）
```
螢幕位置：sx = (wx - camX) * f / z + W/2；sy = horizon + f / z
尺寸 ∝ f / z。永遠由遠到近排序繪製（painter's algorithm）。
```
方塊頂部一條 `rgba(255,255,255,.3)`、底部一條 `rgba(0,0,0,.25)`——兩條線就有立體感。

### 2.5 帶狀多邊形 ribbon（浪、漩渦、流動帶）
沿路徑點 `[x, y, width]` 生成有厚度的多邊形（法線方向左右各 width/2，一圈接回來）。神奈川大浪、星夜流動帶都靠它。**帶子下面要墊量體**（往畫面底部封一片實心），否則像彩虹拱門不像浪。

### 2.6 多邊形掃描線填色 poly(pts, colFn)
colFn(x,y) 逐像素決定顏色（可回 null 跳過）→ 條紋、木紋、筆觸都在這裡做。

## 3. 精靈規格

- 人物 7×9 起跳，字串陣列＋調色盤字典（`'..hhh..'` 格式），換調色盤＝換人。**同一份字串陣列服務所有遊戲**（sprite/PALS 在 shared 層）。
- 放大只用整數倍（1x/2x/3x）。非整數倍會破壞像素格。
- 動畫幀數：idle 呼吸 2 幀、走路 4 幀、事件動作 3 幀就夠（davila7 game-art 的 6-12 幀是給大精靈的，7×9 不需要）。
- 可讀性規則（採自 game-art skill）：**靠明度對比，不靠色相**——重要物件跟背景的明度差 ≥ 25%（這也是變色龍遊戲公平性的底線）。

## 4. 每畫面固定元素

- **HUD 底板**：`rgba(10,12,24,.6~.88)` 半透明黑條，文字用系統字型粗體（像素字型中文字沒有好選擇，不要硬湊）。
- **標題牌**：頂部置中 banner；**倒數計時**右上；玩家計分左下、色塊標識用 CURSOR_COL `['#e8604c','#4fb36b','#5b8fe0','#f2c14e']`（p50 明度差已檢查）。
- 玩家游標：2px 描邊方框＋中心點，蓋章／確認動作放一個 0.15s 的擴散框。
- **名牌是必要元素，不是裝飾**：任何遊戲、任何視角，**每個玩家角色頭上都要掛名字**。
  大螢幕上一堆同款小人，只靠配色認不出哪個是自己——尤其分割畫面到 8-12 格時。
  一律用 DOM 疊層（`.nameTag`）而不是畫進 canvas：中文在低解析度像素緩衝裡糊掉，
  而且名字要能容納五個字。錨點取「角色腳底 − 精靈高度 − 4px」，換算成螢幕座標後定位；
  角色跳起來、旋轉、被外推移動時名牌都要跟著走。
- **配色不夠人數時，第二輪往亮推，不要 `% 8` 直接繞回去**：`CHARA.PLAYERS` 只有 8 組，
  但分割畫面最多 12 人。第 9 個人直接 `% 8` 會跟第 1 個人**一模一樣**——
  兩個同色小人，那兩個人都認不出自己是哪隻，名牌那條規則就白寫了。
  用 `CHARA.palFor(i)`：第二輪整組往白色混 **42%**，色相不變（還是「紅隊」）、
  明度差得開（實測第一輪 vs 第二輪明度比最差 1.4:1、最好 2.0:1；
  0.34 太近、0.46 開始像「白色加一點顏色」，色相反而認不出來）。
  **往亮推不往暗推**——畫面底是深色的，暗色會糊進背景。
  ⚠️ 換要換在 `CHARA.sprite` 裡面，精靈、名牌、游標、記分板才會一致；
  只改記分板的話畫面上還是兩隻同色小人。精靈快取的 key 吃配色的 `name`，
  所以第二輪一定要給不同名字（`紅·2`），否則會拿到第一輪的快取圖、顏色根本不變。
- **大螢幕上的名單不要靠捲動**：實測 1080p 一列 89px（含間距 99px）、
  可視高 670px，**只塞得下 6 列**。超過就分欄，別做捲軸——沒有人會去捲電視。
  分欄要**填滿左欄再填右欄**，不是左右交錯：名次表左右跳著讀是災難。
- **字級用 `vmin` ＋ `clamp()`，不要用 `rem` 寫死**：這些是隔三公尺看的東西。
  實測 1920×1080 的記分板：標題 49.7px、名字 43.2px、分數 54px。
  `rem` 寫死的話螢幕再大字也不會變大。
- **分割畫面另外要有格內 HUD**：每格左上角一張小標籤放該玩家的即時狀態
  （分數／距離／連段），左側色條對應角色配色。理由有二：全域記分板在 10 格時
  會蓋掉整欄；而且角色跳出格外或還沒進場時，狀態仍然要看得到。第一排的標籤
  要自動讓開頂部 HUD。

## 5. 已知地雷

- WebGL 量測要 `gl.finish()`，否則只量到 submit；重建 context 前要 `WEBGL_lose_context.loseContext()`，不然瀏覽器靜默丟舊 context 產生假數字。
- 天空色帶高度取整會留 1px 縫——先鋪滿最後一色再畫帶。
- 抖動漸層跨越大面積時 punch k 取 2~2.5；交界窄的地方取 4~5。
- 跨螢幕色彩再現：ΔE < 40 的顏色差異玩家分不出來（實測），遊戲判定不得依賴細微色差。

# 為什麼是 Durable Object，以及它到哪裡為止

這份不是教學，是**這個 repo 的架構取捨紀錄**：DO 在這四款遊戲裡各自扮演什麼、
不用它做不做得出來、人數往上加會先撞到什麼、以及真正的線上遊戲是怎麼做的。

數字分兩種，文中都標清楚了：**實測**（這個 repo 或官方文件量到的）與
**推算**（從上限和上報率算出來的）。這個 repo **實測沒有超過 12 人**，
所有百人以上的數字都是推算，要當真得先跑 `tools/fakeclients.mjs`。

---

## 一、DO 在這四款遊戲裡其實不是同一個角色

看 `worker/room.js` 的 switch 就知道，四款遊戲對 DO 的依賴差很多：

| 遊戲 | DO 做什麼 | 需要中立第三方嗎 |
|---|---|---|
| 滑雪下坡 | **只轉發＋記錄**。手機自己算跑動，`skiRun` 帶著 x／速度／騰空上來，DO 轉給主控再寫進 log | 不用 |
| 砸罐子 | 同上。`canScoreEvt` 的註解就寫著「host 模擬出來的得分事件」 | 不用 |
| 一二三木頭人 | **DO 判定**。`freezeAct` 用 client 時間戳比「有沒有在轉身之前完成」 | 要 |
| 名畫變色龍 | **DO 最權威**。用種子長出跟主控一模一樣的小人位置、判命中、跑 250ms 搶快窗 | 要 |

真正吃「中立裁判」的只有兩款，另外兩款 DO 是郵差兼書記——但那個書記角色不能省，
匯出的 JSON 是整個 Phase 0 量測的產物。

> ⚠️ **「用 client 時間戳判輸贏」不是 DO 的功能，是我們的設計。**
> DO 只是剛好是個中立的地方可以放這段邏輯。搬到主控筆電上一樣成立——
> 主控是電視不是參賽者，沒有球員兼裁判的問題。分清楚這件事，
> 下面「不用 DO 行不行」才有辦法討論。

## 二、不用 DO 做得出來嗎

做得出來，而且**會更快**。

可行的是 WebRTC DataChannel：手機直連主控筆電，只留一個極小的 signalling 端點交換
SDP（一支 Worker 加 KV 就夠，不用 DO）。同一個 Wi-Fi 下是個位數毫秒，
而我們**實測的 RTT 地板是 ~150ms**（HiNet → wnam 的 DO；放 apac 反而變 ~360ms，
因為這條 ISP 從 SJC 入網）。

會失去的東西全部在營運面，不在技術面：

- **HTTPS。這條最致命。** `deviceorientation` / `devicemotion` 需要 secure context，
  所以「在筆電跑個 node server、大家連區網 IP」這條路走不通——iOS 在 `http://` 下
  不會給感應器權限，滑雪和砸罐子直接死。自簽憑證讓每個人點過警告？家宴當天不可能。
- 掃 QR 就能玩、自動重連、自動匯出 JSON，這些現在是白拿的。
- WebRTC 在某些網路要 TURN 中繼，又繞回來需要伺服器。

**結論：技術上不需要 DO，但為了「當天不用設定任何東西」而付的這點錢很划算。**
真的想省，最合理的是混合——signalling 用 Worker，遊戲資料走 P2P，
DO 只在需要裁判的那兩款開。

## 三、DO 唯一無敵的地方，剛好就是它的天花板

分散式系統最煩的問題是「確保同一時間只有一個人擁有這份狀態」。
正常解法是共識系統（Raft／etcd）、leader election、分散式鎖、或資料庫的樂觀鎖——
每一種都要營運一套叢集。DO 把這件事變成**語言層的原語**：
`env.ROOM.idFromName("ABCD")`，然後你就是唯一的擁有者。

延伸出來的兩個好處：

- **運算跟狀態黏在一起。** 那個 250ms 搶快窗就是一個 `setTimeout` 加一個 `Map`。
  換成「無狀態 serverless + Redis」，同樣的功能是好幾個網路來回，還要自己處理 race。
- **儲存跟執行在同一個交易裡。** input／output gate 讓你不可能觀察到撕裂的狀態。

> actor 模型本身不新——Erlang 的 process、Microsoft Orleans 的 virtual actor、
> Akka cluster sharding 都是同一套。DO 的新意在於**沒有叢集要營運，
> 而且從 edge 就能定址**。講白一點，它是「Erlang 的 process model 綁上 CDN」。

### 但那個無敵就是天花板

**單一擁有者讓它正確，也讓它無法水平擴展。** 一個 object 就是一條執行緒，
加機器救不了熱點。這是本質，不是最佳化問題。

| 情境 | 為什麼 DO 不對 |
|---|---|
| **熱點 key** | 那個爆紅的文件、十萬人的直播聊天。單執行緒＋每個 DO 1,000 req/s 軟上限，只能往下拆，拆到最後是自己寫了一個爛資料庫 |
| **不能按 key 切的東西** | 全域排行榜、全文檢索、分析型掃描。跨 object 沒有 join，要自己寫 fan-in 樹 |
| **地理** | `locationHint` 只在建立時生效，之後不會搬。全球使用者共用一個 object，就一定有人吃 300ms。單一 DO 沒有多區複本 |
| **重運算** | 30 秒 CPU／請求、單執行緒。一個 DO 在算重的東西時，它自己的所有使用者一起卡 |
| **動作遊戲** | 沒有 UDP，TCP head-of-line。我們自己量到的 RTT 地板就是 ~150ms |
| **費用形狀** | 按「活著的時間」計費（128MB × 秒數），不是按做了多少事。長壽但閒置的物件＝在燒錢發呆——README 的三層計費防呆就是為此存在 |
| **可攜性** | 這個程式模型真的綁死 Cloudflare。搬家等於重寫 actor 層 |

**判準只有一句：問題能不能自然切成很多個「各自只有一個擁有者」的小單位？**
能（房間、文件、對局、聊天頻道、某個 key 的限流、一個工作流實例）就接近無敵；
不能（一個大家共用的熱點）就會用「看起來很優雅但撞牆撞得很硬」的方式失敗。

## 四、人數往上加，先撞到什麼

### 派對遊戲的形狀不是 N²

這點很重要，別拿 MMO 的扇出來嚇自己。看 `pointer` 那段：DO 只 `toHosts()`——
**N 支手機進來，只往 1 台主控出去**。所以是 2N，不是 N²。

這個 repo 實際的上報率（讀 `public/client.html`）：

| 型態 | 遊戲 | 每人每秒 |
|---|---|---|
| 串流型 | 變色龍／砸罐子 游標 | 15（66ms 節流＋位移門檻） |
| 串流型 | 滑雪 `skiRun` | 10（60fps 的每 6 幀） |
| 事件型 | 木頭人 `freezeAct`、砸罐子 `canThrow` | 一回合幾筆 |

對上官方的 **1,000 requests/秒 per DO 軟上限**（推算）：

| 人數 | 15Hz 游標 | 10Hz 滑雪 |
|---|---|---|
| 12（現在的上限） | 180 ✅ | 120 ✅ |
| 50 | 750 ✅ | 500 ✅ |
| 100 | 1,500 ❌ | 1,000 ⚠️ |
| 300 | 4,500 ❌ | 3,000 ❌ |

換算：**15Hz → 66 人就到頂**，降到 5Hz → 200 人，降到 3Hz → 333 人。

### 300 人的尾牙怎麼做

不是「DO 做不到 300 人」，是「300 支手機每秒各送 15 筆」做不到——
**換成自架也一樣要處理**。由便宜到貴：

1. **依人數調上報率。** 超過 50 人就把游標降到 3–5Hz。代價是游標變頓，
   但電視上 300 個游標本來就是一團雜訊，根本看不出哪個是自己——所以這個代價不存在。
2. **改遊戲設計，這才是正解。** 300 人的大亂鬥不該有 300 個游標，應該是聚合機制：
   大家一起狂點，畫面上是一條長條或一群小人往前衝，每人只回報「有沒有在動」，
   1Hz 就夠。300 × 1Hz = 300/s，一個 DO 輕鬆。
3. **分片。** 一個 DO 帶 50 人 × 6 間，外加一個 1Hz 收總分的 DO。
   標準做法，而且 300 人的尾牙本來就該分隊。

### 但 DO 不會是先垮的那一個

- **場地 Wi-Fi。** 300 支手機打同一個 AP，這幾乎一定先垮。而且我們吃的是
  穩定的低延遲，不是頻寬。
- **開場那一分鐘 300 次掃碼。** join 的突波比整場的穩態流量還兇。
- **主控端渲染。** 名牌是 DOM 疊層（中文在低解析度 canvas 會糊，不能改成畫進 canvas），
  300 個 DOM 元素每幀更新是真的貴；分割畫面上限是 12。300 人一定得換成聚合視覺。

## 五、真正的線上遊戲是怎麼做的

先修一個常見的數字：WoW 的戰場上限是 **40v40**（奧特蘭克山谷），不是 200。
100v100 的是 Ashran，而那個規模在當年就是出了名的難搞。開放世界則靠
sharding／layering——**同一個區同時存在好幾份平行複本**，人多就把玩家分流過去。

這件事本身就是答案的一半：**真正的線上遊戲不是「解決了很多人同場」，
是「用盡各種手段讓同場人數維持在低的數字」。**

### 六件事

1. **Tick loop，不是請求／回應。** 伺服器是一個固定頻率的模擬迴圈（10–30Hz）。
   client 送的是**輸入**，server 跑權威模擬，回送**快照**。它不「回應請求」，
   它把輸入累積到下一個 tick 一起算。我們這個 repo 是 relay 模型——收到就轉發——
   那是派對遊戲的形狀，不是 MMO 的形狀。
2. **UDP，而且自己寫可靠層。** 位置封包掉了不用重傳，下一個就蓋過去了；
   TCP 的 head-of-line blocking 會讓一個掉包卡住後面全部。所以自己分通道：
   聊天／掉寶走「可靠有序」，位置走「不可靠但有序號」。
   （WoW 自己是 TCP，是個例外——它是 tab-target、GCD 1.5 秒的慢節奏，
   忍得住 200–400ms。**通訊協定是被戰鬥節奏決定的。**）
3. **Area of Interest——N² 的解藥。** 地圖切格子，每個玩家只訂閱自己那格＋周圍八格。
   每 tick 從 O(N²) 變成 O(N × 鄰居數)。200 人的戰場，視野裡通常只有 20–30 人。
4. **Delta 快照＋量化。** 只送「跟你上次確認過的快照相比改變了什麼」。
   位置不送 float64，送格子內的 16-bit 定點數再 bit packing。
   Quake／Source 的 delta snapshot 是這套的祖宗。真正的頻寬勝負在這裡。
5. **優先權預算。** 封包大小固定，塞不下就不塞。每個實體按「距離、多久沒更新、
   是不是正在打我」算優先權，填滿為止。**遠處的人 2Hz，旁邊的人 20Hz。**
   200 人混戰能跑起來靠這個，不是硬體夠猛。
6. **客戶端預測＋伺服器和解＋插值。** 自己的移動立刻在本機演算並附序號送出，
   server 回權威狀態，client 重播還沒被確認的輸入。別人則渲染在 **100ms 之前的過去**，
   抖動就看不出來。命中判定再做 lag compensation——server 倒轉回射擊者當時看到的畫面。

### 為什麼還是要設上限

不是網路不夠，是四件事同時撞牆：伺服器 CPU（200 人的技能／AI／碰撞 × 20–30Hz）、
**客戶端**（渲染 200 個帶不同裝備的角色，通常比伺服器先死，WoW 那個「降低法術效果」
的選項就是為此存在）、每個 client 的頻寬是 O(N)、以及**好不好玩**
（200 個人擠成一團本來就不有趣）。

> **EVE Online 走的是另一條極端**：單一宇宙不分服，一個星系＝一個節點，
> 人太多就開 time dilation——把時間流速降到 10%，用「大家一起變慢」
> 換「不要崩潰」。3,000 人打一場，是真的用慢動作打完的。

### 對照回 DO

| 需要的 | DO 有沒有 |
|---|---|
| 一個實例＝一個擁有者＝一條執行緒 | ✅ 天生就是這個形狀 |
| Tick loop | ✅ 自己在裡面 `setInterval` 就好 |
| AoI、delta、優先權預算 | ✅ 都是應用層邏輯，跟後端無關 |
| **UDP** | ❌ 只有 WebSocket，TCP head-of-line |
| **選機房、綁核心、掛 profiler** | ❌ 位置建立時就定了，也進不去看 |

**做 WoW 那種節奏（tab-target、忍得住 200ms）的 MMO，DO 架構上成立**——
WoW 自己就用 TCP。加上 tick loop 和 AoI 之後，一個 zone DO 大概 100 人上下
（推算：10Hz、每人每 tick 併成一包，撞 1,000 req/s 軟上限），再多就開複本——
這剛好就是 layering 的做法。

費用不是問題：一個 zone DO 掛 24 小時是 `0.128GB × 86,400s ≈ 11,059 GB-s`，
以付費方案 US$12.50／百萬 GB-s 算是**每天 US$0.14、每月 US$4.15**；
100 個 zone 每月約 US$415。

**但 FPS、格鬥、任何需要 60Hz 和 lag compensation 的就不要想了**——
沒有 UDP 這件事沒有繞路。那種要的是「離玩家近的機房裡一台自己的機器、
跑自己的 UDP 迴圈」，而那正是 DO 刻意不提供的東西。

## 六、誰付得起這個錢：鎖在哪一層

DO 是按存活時間計費的，所以「誰可以開房間」就等於「誰可以花到你的錢」。
這件事有一個很容易做錯的直覺：**把主控頁面放到 Cloudflare Access 後面**。

那個做法擋不住任何東西。DO 不是 `/host` 開出來的，是 `/ws/<房號>` 開出來的——
路人不用打開任何頁面，直接連 `wss://…/ws/ABCD` 就生得出一個 DO 掛在那裡計費。
**保護頁面沒有保護到花錢的那條路徑。**

正確的位置只有一個：**Worker 裡，`env.ROOM.get()` 之前**。
拿到 stub 就等於生出 DO 了，之後才拒絕已經來不及——費用是從那一刻開始算的。

做法是一張 HMAC 簽的房間憑證：主控（過 Access）打 `POST /api/room` 換一張，
QR 網址帶著它，掃 QR 的人不用登入。`/ws`、`/export`、`/whereami`、`/close`
沒有有效憑證一律 403。設定方式與驗收清單見 README 的「誰可以開房間」。

線上實測（`mahou.ai-apps.work`，設好 `ROOM_SECRET` ＋ Access 之後）：
四條 DO 路徑無憑證全部 403、`/host` 與 `/api/room` 302 導到 Access 登入頁、
`/client` `/ambient` `/audio` `/voice` `/arts` 全部 200。

> 設定時踩到的：`ROOM_SECRET` 沒設到部署的那支 Worker 時，前端是新的、
> 後端的檢查卻是空的——**`/close/<任意房號>` 回 200 就是還沒鎖上**，
> 那比看主控台的字條可靠（字條只知道「換不到憑證」，不知道為什麼）。

順帶一個容易漏的細節：**Access 的 JWT 要真的驗簽**，不能只看
`Cf-Access-Jwt-Assertion` 這個 header 在不在。Access 沒有蓋到的路徑，
Cloudflare 不會幫你把使用者自己送的同名 header 拿掉。

背景模式 `/ambient` 與 `/audio/*` 刻意不鎖——它們本來就不碰 DO（見第二節），
鎖它們只是找自己麻煩。

還有一件跟 DO 無關但同樣重要的：**`workers.dev` 要關掉**（`workers_dev = false`）。
Access 綁在自訂網域上，`*.workers.dev` 那條進來的請求不經過它——留著等於開一扇沒鎖的側門。

這一層的完整驗收清單、以及上線前安全複查的結果（複查過什麼、修了什麼、
哪些是知道但決定不改的），寫在 README 的「誰可以開房間」與「安全複查」。

## 七、這個 repo 的位置

我們的房間正好落在 DO 最擅長的那一格：**一場遊戲＝一個房間＝一個擁有者、
12 個人、活一兩個小時就結束**。所以它幾乎不用調就會動，而且免費方案就跑得完。

而 300 人那題的答案是：**瓶頸不是 Cloudflare 不夠力，是「一場遊戲＝一個擁有者」
這個切法，在 300 個獨立游標的設計下不成立了。** 修法是改遊戲設計讓它重新可切，
不是換後端。換自架也一樣要面對——只是會用比較不優雅的方式炸。

# #6 名畫變色龍（找不同）— 設計與技術規格

> 原型頁：[`/public/game6.html`](../public/game6.html) → 部署後開 `https://<網域>/game6`
> 狀態：視覺原型完成、玩法待實作、**陀螺儀瞄準未驗證（最大風險）**

---

## 1. 這個遊戲是什麼

大螢幕顯示一幅**世界名畫的 pixel art 版本**。畫裡藏著幾隻「變色龍小人」——它們會把身體顏色染成腳下背景的顏色，藏在筆觸裡。玩家用手機當印章，在 20 秒內把牠們找出來蓋章。

比起原本的「一堆小人裡找戴帽子的」，改成名畫有三個實際好處：

- **畫面本身有觀賞價值**。找不到的人也有東西可看，長輩會開始聊「這張我看過」。
- **偽裝有了天然的藏身處**。名畫的筆觸、色塊、明暗天生就是掩護，不用另外設計干擾物。
- **一畫一主題**，換畫就是換關卡，內容擴充成本極低。

---

## 2. 玩法

| 階段 | 時間 | 大螢幕 | 手機 |
|---|---|---|---|
| 揭幕 | 3 秒 | 畫作淡入、標題牌顯示畫名與作者 | 顯示「準備」 |
| 搜尋 | **20 秒** | 小人已藏好，計時條倒數 | 瞄準 ＋ 蓋章 |
| 揭曉 | 5 秒 | 所有小人亮框，蓋中的打勾、蓋錯的打叉 | 顯示本輪得分 |

- 蓋中 **+3 分**，蓋錯 **−1 分**（避免亂槍打鳥）
- 同一隻被多人蓋中時，由 DO 依 client 時間戳判先後，**只有最快的得分**（探針 A 的正式應用）
- 一輪固定 20 秒，**這是刻意的硬上限**：控制手機發熱、控制注意力疲勞，也讓一局能塞進吃飯的空檔

### 為什麼是 20 秒

沿用 handoff §8.5 對相機玩法的同一套理由：**發熱、電量、疲勞**。這個遊戲雖然不開相機，但陀螺儀持續取樣 ＋ 高頻上報仍有成本，而「盯著畫面找東西」的視覺疲勞比想像中快。寧可一輪短、多玩幾輪。

## 3. 變色龍偽裝機制

小人放好位置後，**從底圖取樣它腳下與周圍的顏色**，把身體色朝那個顏色內插：

```
body = lerp(自身色, 背景取樣色, 偽裝強度)
```

偽裝強度是一個 0–1 的連續參數，直接對應「小人與背景的色差」。這帶來一個重要性質：**難度可以連續調整，而且可量測**。

### 難度就是 ΔE

顏色反應那一輪（房間 MGFY）已經量到一組硬數據：

| ΔE | 答對率 |
|---|---|
| ~100 | 5/5（100%） |
| ~40 | 3/5（60%） |
| ~15 | 2/5（40%） |
| ~7 | 3/5（60%，等同亂猜） |

**跨螢幕色彩再現讓 ΔE < 40 的判斷退化成擲骰子。** 同一把尺直接套用在這裡：把偽裝強度換算成小人與背景的 ΔE，就知道題目落在「看得出來」還是「純猜」哪一區——不用靠現場感覺調參。

建議分級（待實測校準）：

| 對象 | 目標 ΔE | 偽裝強度 |
|---|---|---|
| 幼兒／長輩 | 55–70 | 30–45% |
| 一般 | 35–50 | 55–70% |
| 高手 | 22–32 | 78–88% |

低於 ΔE 20 不要用——那不是難，是不公平。

### 公平的破綻：眨眼

完全靜止的偽裝小人可能真的找不到。所以每隻小人會**隨機眨眼**，眼睛那兩格閃一下深色。這是唯一保證能被看見的線索，也讓「盯著畫面掃描」變成有意義的行為而不是碰運氣。眨眼頻率（目前 2.2–4.8 秒一次）是可調參數，等同於難度的第二個旋鈕。

## 4. 手機輸入

### 主方案：陀螺儀瞄準 ＋ 點擊蓋章

手機對著電視當雷射筆，游標映射到大螢幕，點擊蓋章。派對感最強。

**但這是全清單最大的技術風險**——handoff §8.2 的三個數字完全沒量過：

| 要量的 | 方法 | 為什麼決定成敗 |
|---|---|---|
| 漂移速度 | 歸零後手機靜置桌上 60 秒，記錄游標位移 | 漂太快就要每輪歸零，甚至每 15 秒 |
| 手抖半徑 | 靜握瞄準時游標的抖動範圍 | **直接決定小人要畫多大**，這是關卡設計的輸入 |
| 到達時間 | 從螢幕一角移到對角所需時間 | 決定 20 秒夠不夠掃完整張畫 |

**開發前先花一小時做這個探針。** 數字沒出來之前不要動主方案——如果手抖半徑是螢幕寬度的 8%，小人就得畫得比現在大三倍，整個視覺設計都要重來。

### 必備降級：手機縮圖直接點

手機上顯示同一張畫的縮圖，用手指直接點。用的是**已驗證最可靠的觸控絕對座標**（Stage 0：狂點 3 秒 0 掉包）。

這不是備案，是**必須實作的並行方案**：
- 陀螺儀在部分機型上可能根本不堪用
- 有人手會抖（長輩尤其）
- iOS 的權限流程多一道關卡

現場要能一鍵切換，不能讓某個人整局坐在旁邊。

## 5. 延遲策略

**150ms 的 RTT 地板完全不影響這個遊戲的公平性**，只要判定用對時間戳：

- 蓋章時刻用 **client 的 `performance.now() + offset`**（已對時到伺服器時間軸），不是伺服器收到的時間
- DO 只負責排序與去重：同一隻小人被多人蓋中時比較 client 時間戳
- 網路延遲只影響「印章什麼時候出現在電視上」，不影響誰得分

這套機制跟 #1 木頭人共用，先做木頭人就等於先把這裡也做完。

## 6. 名畫清單

四張已實作，全部是**程序化描述**（多邊形控制點 ＋ 數學曲線），不是點陣圖資源：

| 畫作 | 作者 | 為什麼適合 | 偽裝掩護 |
|---|---|---|---|
| 星夜 | 梵谷 1889 | 辨識度最高，流動筆觸 | 漩渦與流動帶提供大量中間色 |
| 神奈川沖浪裏 | 葛飾北齋 1831 | 構圖強烈，藍白對比 | 浪的層次條紋、泡沫飛沫 |
| 吶喊 | 孟克 1893 | 色彩最鮮明，人物好認 | 橘紅色帶、橋的木紋 |
| 睡蓮 | 莫內 1906 | 滿版重複紋理，最難找 | 幾十片蓮葉是天然的干擾物 |

**難度天生不同**：睡蓮的重複紋理最難，吶喊的大色塊最簡單。這可以直接當關卡順序。

擴充候選：蒙娜麗莎（暗色調，難）、格爾尼卡（灰階，超難）、清明上河圖局部（中式，家宴有話題性）、富春山居圖（同上）。

### AI 在這裡的角色

不是生成圖像，而是**生成題目與旁白**：

- 出題變化：「找出戴帽子的」「找出沒在笑的」「找出比別人矮的」——同一張畫可以出很多題
- 畫作小知識：找到後電視播一句「梵谷畫這張時人在精神病院」，長輩會有反應
- 難度自動調整：依前一輪的答對率動態調偽裝強度

這些都是純文字生成，成本低、失敗了也不影響遊戲進行。

## 7. 讓 pixel art 更精美的技法

`game6.html` 裡實際用到的五招，可以直接搬到其他遊戲：

### 1. 受限調色盤
每張畫只用 **12 色**，取自原作主要色域。少色是 pixel art 好看的第一原因——顏色一多就會變成「縮小的照片」而不是像素畫。

### 2. Bayer 4×4 有序抖動 ＋ smoothstep
低解析度畫漸層的關鍵。但**光有抖動會變成雜訊**——第一版就踩到這個坑（星夜的天空看起來像螢幕壞了）。正確做法是先把混合值用 smoothstep 推向 0 或 1：

```js
const punch = (v, k) => ss((v - 0.5) * k + 0.5);   // k ≈ 2–5
```

色塊變成實心、**抖動只留在交界處**，看起來就像筆觸而不是噪點。

### 3. 色相偏移，不是單純調亮暗
陰影往冷色（藍紫）走、亮部往暖色（黃）走：

```js
const shade = (c, amt) => amt < 0
  ? [c[0]*(1+amt), c[1]*(1+amt*.88), c[2]*(1+amt*.62)]      // 暗部偏冷
  : [c[0]+(255-c[0])*amt, c[1]+(255-c[1])*amt*.92, c[2]+(255-c[2])*amt*.6];  // 亮部偏暖
```

只加減亮度會讓畫面發灰發髒，這一行就能救回來。

### 4. 用形狀描繪，不要用雜訊堆
第一版的星夜天空是靠 `sin` 疊 `sin` 硬湊漩渦，結果推成實心之後整片變平。改成**明確的流動帶與螺旋**（沿路徑生成有厚度的帶狀多邊形）之後立刻像梵谷。

同理，神奈川的大浪第一版是兩條曲線之間填色，右緣被硬切成一道直線；改成「一條由粗變細的帶子 ＋ 底下墊一片水牆量體」才有捲浪的重量感。

**教訓：構圖用形狀，質感用抖動。反過來做就會失敗。**

### 5. 畫一次、快取、只重畫會動的東西
畫作畫進像素緩衝區後存成點陣圖，每幀只做「貼底圖 ＋ 畫小人 ＋ 畫游標」。

## 8. 效能實測

在容器 CPU（軟體渲染，比 Chromebook 慢）上量到：

| 項目 | 數字 |
|---|---|
| 畫作完整重繪（一次性） | **10.7–12.7 ms** |
| 每幀成本（貼底圖＋小人＋游標） | **0.30 ms** |
| 內部解析度 | 320×180 |
| 調色盤 | 12 色／張 |

**畫作再複雜都不影響每幀成本**——這是快取架構的直接結果。對 60fps 的 16.7ms 預算有 55 倍餘裕，換張畫的一次性 12ms 也遠低於一幀，玩家不會感覺到卡頓。

配合 Chromebook 上量到的分割渲染數字（WebGL 12 分割 1.0ms／幀），這個玩法在效能上完全沒有疑慮。

## 9. 開發順序

1. **先做瞄準探針**（一小時）：漂移、手抖半徑、到達時間。數字決定小人尺寸與主方案是否成立。
2. **先做降級方案**（手機縮圖直接點）：它是必備的，而且用已驗證的輸入，可以先讓遊戲跑起來。
3. **接上 DO 判定**：蓋章上報、client 時間戳排序、去重、計分。與 #1 木頭人共用同一套機制。
4. **主方案（陀螺儀）視探針結果決定**。
5. 最後才擴充畫作與 AI 出題。

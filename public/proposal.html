共通技術方案：內部低解析度渲染 ＋ 整數倍放大。
每個畫面在 256×144 這種尺寸畫完，再用 image-rendering: pixelated 放大到全螢幕。三個好處一次拿到：填充率降到 1/50（8 分割輕鬆過關）、美術要求降到最低（一個小人只要 7×9 像素）、風格統一（所有遊戲自動長得像同一套作品）。假 3D 用逐掃描線透視（SFC Mode 7 的原味做法），或 WebGL 片段著色器算地面射線——Chromebook 上兩條路都有大把餘裕。

風格聖經（讓 pixel art「精美」的五條）

找過市集與開源的 pixel art skill：能用的內容很薄（結論見規格書附錄），所以把本 repo 實測驗證的技法自建成 project skill——.claude/skills/pixel-fake3d/SKILL.md，之後所有畫面工作自動遵循。核心五條：

01 · 受限調色盤
每場景 10–14 色。顏色一多就變成「縮小的照片」而不是像素畫。
02 · 抖動要先 PUNCH
Bayer 4×4 有序抖動直接吃連續混合值會變雜訊；先用 smoothstep 把值推向 0/1，抖動只留在交界，才是「筆觸」。
03 · 色相偏移著色
陰影往冷色走、亮部往暖色走。單純加減亮度會發灰發髒。
04 · 構圖用形狀，質感用抖動
漩渦、大浪這種構圖元素用明確的帶狀多邊形畫出來；抖動只負責過渡。反過來做必失敗（星夜第一版的教訓）。
05 · 畫一次、快取
複雜背景畫進緩衝區存起來（實測 11ms 一次性），每幀只畫會動的東西（0.3ms）。畫面再複雜都不影響幀率。
實證
四張名畫（星夜／神奈川沖浪裏／吶喊／睡蓮）已用這套做完，線上 /game6 可玩參數。下面 #6 的畫面就是縮小版星夜。

提案一覽

下面六款依建議開發順序排列。每款都標了手機輸入、延遲判定策略，以及還沒被 Phase 0 驗證過的風險。

HOST SCREEN
#1木頭人・混合指令原型：一二三木頭人 ＋ WarioWare 微型指令
HOW TO PLAY
鬼背對時，電視打出指令：「搖！」「點紅色！」「衝！」——照做才前進。鬼一轉身，指令變成「不要動」，這時任何動作（手機晃動超過閾值、點螢幕）都算犯規退後。混合指令讓它不只是反應快慢，還考驗切換注意力，小孩跟長輩各有優勢。最後看誰錯最少。
PHONE INPUT
點擊 ＋ 搖動 ＋ 「靜止偵測」（加速度變異數低於門檻）。全部是 Phase 0 已驗證的輸入，零新技術風險。
LATENCY
可以做到完全公平。鬼轉身時刻由 DO 蓋伺服器時間戳廣播；玩家動作用已對時的 client 時間戳判定，不是用伺服器收到的時間。150ms 的傳輸延遲因此完全不影響判定——這是整個平台最重要的一招。
RISK
低。唯一要調的是「不動」的靈敏度：手抖、呼吸、放桌上都不該誤判，門檻要做成可現場調的滑桿（比照 Stage 0 的搖動參數）。
延遲免疫輸入已驗證開發 1–2 天建議第一個做
PLAYER VIEW · 1/8
#3下坡滑雪・第一人稱原型：SFC 瑪利歐賽車 Mode 7 ＋ 3D 太空哈利
HOW TO PLAY
搖得越快滑得越快（已有原型）。升級成第一人稱假 3D，電視 8 分割同時看所有人。加入轉彎閃避樹木、跳躍吃跳台加速。
PHONE INPUT
加速＝搖動（已驗證）。轉彎＝手機左右傾斜（gamma，開局要歸零校準）。跳躍＝點螢幕——刻意選離散輸入，因為點擊延遲已知穩定，比「向上甩」可靠得多，也不會跟搖動的加速度訊號打架。
LATENCY
轉彎是連續控制，150ms 下手感會鈍。對策：賽道加寬、樹距拉大、轉向做慣性平滑，把「需要精準微調」的情境整個設計掉。跳躍用 client 時間戳判定起跳點，不受延遲影響。
RISK
中。傾斜控制的手感是 handoff §7 要量的東西，還沒驗證。建議同時保留「不轉彎」的簡化模式當退路——現有原型已經證明純搖動版可玩。
延遲中敏感搖動已驗證傾斜未驗證已有原型
HOST SCREEN
#4砸罐子・彈射保齡原型：憤怒鳥 ＋ Wii Sports 保齡球
HOW TO PLAY
遠處堆著一座方塊塔（罐頭、木箱、年獸），拉弓發射把它砸垮，倒得越多分越高。堆疊物用格子化的 pixel 方塊，倒塌時整座垮下來——視覺爽度最高的一款，旁邊看的人會跟著叫。
PHONE INPUT
兩種擇一，建議都做：彈弓模式——手指按住往後拉，放開發射（觸控拖曳，精準）；甩投模式——揮動手機，加速度峰值決定力道（派對感強，精準度低）。長輩用彈弓、小孩用甩投。
LATENCY
完全免疫。發射後就只是物理演算：手機只上傳發射參數（角度、力道、旋轉），伺服器發同一組亂數種子，各端跑決定性物理算出同樣結果。網路延遲只影響「球什麼時候出現」，不影響公平也不影響手感。
RISK
低—中。要寫一個簡化的方塊堆疊物理（格子化剛體、只處理軸對齊碰撞），這是六款裡程式量最大的，但完全離線可測、跟網路無關。
延遲免疫觸控＋揮動需寫物理視覺爽度最高
HOST SCREEN · 20s
#6名畫變色龍原型：超級變色龍 MECCHA CHAMELEON ＋ 世界名畫
HOW TO PLAY
大螢幕是一幅 pixel art 名畫（星夜、神奈川沖浪裏、吶喊、睡蓮，全部程序化生成、零圖檔），裡面藏著幾隻「變色龍小人」——牠們取樣腳下的畫作顏色把自己染過去。20 秒內用手機蓋章抓出來，蓋中 +3、蓋錯 −1。找不到的人也有名畫可看，長輩會開始聊「這張我看過」。
難度＝ΔE，可量測
偽裝強度是連續參數，直接換算成小人與背景的 ΔE 色差——套用顏色反應實測的同一把尺（ΔE<40 等於亂猜）：長輩 55–70、一般 35–50、高手 22–32。公平破綻是隨機眨眼。
PHONE INPUT
主方案：陀螺儀瞄準＋點擊蓋章。必備降級：手機縮圖直接點（已驗證的觸控座標）——先做降級版讓遊戲成立，主方案等探針數字。
RISK
陀螺儀是全案最大未驗證風險：漂移、手抖半徑、到達時間三個數字直接決定小人要畫多大。開發前先花一小時做瞄準探針。視覺原型已上線（/game6），規格見 docs/game6-masterpiece.md。
延遲免疫四張名畫已完成陀螺儀未驗證觀賞價值最高
HOST SCREEN · 4×4
#9翻牌記憶・搶配對原型：神經衰弱 ＋ 世界のアソビ大全51
HOW TO PLAY
開局全部翻開 10 秒給大家背，然後蓋起來開搶。翻對一對得分並保留，翻錯蓋回去。小孩常常贏大人——這對家宴氣氛的價值超過遊戲本身。
PHONE INPUT
手機顯示同樣的牌陣縮圖，直接點座標。用的是最可靠的觸控絕對座標，Stage 0 已驗證狂點 0 掉包。
LATENCY
搶同一張牌＝探針 A 的正式應用。翻牌意圖用 client 時間戳排序，DO 判先後——RTT 差 30ms 的人不會永遠輸。
RISK
最低，但張數上限由手機觸控精度決定（見下表）。64 張是硬上限，再多手指點不準。

HOST SCREEN · RELAY
#11接力快炒・辦桌大戰原型：Overcooked 煮過頭（拿掉自由移動）
HOW TO PLAY
兩隊接力出菜。每人固定一個工位，做完自己那道工序傳給下一位。五個系列各四到五道菜：中式熱炒（翻鍋）、中式炸物（下鍋、控時、起鍋）、西式炸物（裹粉、油炸）、義式 Pizza（揉麵、拋餅、鋪料、進爐）、日式串燒（翻面、刷醬）。菜色越後面越需要精準控時。
PHONE INPUT
每個工序對應一種已驗證輸入：翻鍋＝搖動、起鍋＝時機點擊、揉麵／拋餅＝拖曳、灑料＝傾斜。整套下來剛好把四種輸入都用上，是最好的綜合壓力測試。
LATENCY
設計上直接免疫。關鍵決定：不做自由移動——Overcooked 最貴、也最吃延遲的就是角色跑動。改成固定工位後，每個工序都是「本地做完、結果上報」，150ms 只影響電視上的動畫時機。
RISK
中。程式量不大但內容量大（5 系列 × 4–5 道菜 × 每道 3–4 個工序）。建議先做兩個系列驗證手感，確認好玩再量產菜色。
延遲免疫四種輸入全用上內容量大合作＋接力

開發順序（規格書 §7 的批次表）

  • 批次 0 — 共用引擎：把 game6 與 bench 的渲染配方抽成 engine/pixel.js · mode7.js，新寫 stamp.js（client 時間戳判定協定）；同時做陀螺儀瞄準探針。
  • 批次 1 — #1 木頭人：全部已驗證輸入、延遲免疫、1.5 天可玩，順便把時間戳判定機制上線。
  • 批次 2 — #9 翻牌 ＋ #6 降級版：翻牌產出探針 A 的正式數據；名畫變色龍的畫已經畫好，降級版一天。
  • 批次 3 — #3 滑雪升級 ＋ #4 砸罐子：共用 Mode 7 管線；滑雪順便量傾斜手感（§7 A/B 半場），砸罐子的決定性物理可完全離線開發。
  • 批次 4 — #11 接力快炒：先做熱炒＋Pizza 兩系列驗手感，好玩再量產菜色。
  • #6 陀螺儀主方案：只在探針三數字合格後開工。
